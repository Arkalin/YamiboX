# 下载、缓存与封面存储

本文说明用户主动保存的离线内容、可再生成的技术缓存和持久化封面的边界，以及队列、文件和平台后台任务之间的协作。阅读内容加载与投影见[阅读器设计](readers.md)，共享数据库和身份合并见[持久化与作品身份](persistence-and-identity.md)，账号转换见[账号与应用生命周期](account-lifecycle.md)。

## 1. 三类数据不能混用

| 类别 | 主要内容 | 生命周期与责任 |
| --- | --- | --- |
| 主动下载 | 小说源页面与文档、选择保留的正文图片、漫画源页面与图片、论坛附件 | `DownloadStore` 管理队列和已保存条目；不参与普通图片缓存的容量淘汰 |
| 技术缓存 | 论坛首页、板块和帖子页面；小说及漫画投影；普通图片原始字节与解码结果 | 可重新获取或计算；允许失效、淘汰及用户清理，不作为离线保存承诺 |
| 持久化封面 | 封面索引、自动与手动选择、显示偏好、已获取的原始图片 | `ContentCoverStore` 管理引用和文件；不随普通图片缓存清理或淘汰 |

浏览过某页、图片命中过缓存、设置过封面，都不等于下载完整作品。漫画下载按章节帖子保存，小说下载按论坛源页面保存，不是按排版后的屏幕页保存。

`owner_name` 是历史保留的数据库字段名，表示作品分组，不表示登录账号：漫画使用目录身份，小说使用帖子与作者视图组成的分组键。当前下载和封面数据保存在设备共享库中，**不是按账号 UID 分目录存储**。账号切换会停止旧会话的下载执行，但不自动删除已经保存的离线内容或封面。

## 2. 代码归属与能力接口

- [共享下载目录](../../Sources/YamiboXCore/Reader/Shared/Download/)：Domain 定义任务、管理投影与能力协议；Application 执行队列与传输；Data 实现数据库和文件存储。
- 小说、漫画分别在各自的 `Application` 目录提供 `DownloadWorkProcessingStrategy`；论坛附件由 [Forum](../../Sources/YamiboXCore/Forum/) 提供下载请求、执行器和存储适配。
- [图片基础设施](../../Sources/YamiboXCore/Infrastructure/Images/)统一加载原始字节；[Library/Data](../../Sources/YamiboXCore/Library/Data/)拥有封面索引和持久化图片。
- [UI 下载功能](../../Sources/YamiboXUI/Features/Download/)负责列表、选择、确认和错误展示；[平台后台任务](../../Sources/YamiboXUI/Platform/BackgroundTasks/)适配系统调度，不承担业务队列存储。

消费方使用所需的窄能力，如 `DownloadQueueStoring`、`DownloadManagementStoring`、`DownloadImageAssetStoring`、`MangaDownloadStoring` 或 `NovelDownloadStoring`，而不是为了读取队列就依赖整个 App 账号依赖包。装配根组合完整的 `DownloadStoring` 并注入同一存储实例。

## 3. 入队、执行与完成

### 入队的提交边界

小说与漫画在自己的单次数据库写事务内完成请求规范化、已有下载或任务检查、分组身份解析和新任务写入。公共 `enqueueNewWork` 只在该事务内使用，生成 `work_id`、全队列递增的插入序号，并保存目标图片引用；成功提交后才发送下载变更通知。

重复请求返回已有下载或已有队列任务，不产生第二个相同条目。小说的更新入队入口允许刷新已保存源页面，区别于普通入队的跳过已有下载行为。附件的请求元数据和新队列记录也在同一事务保存；重复入队可以更新请求信息而不替换原任务。

这里的原子性是**队列数据库记录的原子提交**，不是网络、SQLite 和文件系统之间的全局事务。文件写入采用原子替换，并由各存储操作负责失败回滚或后续清理；不能从一条成功的 SQL 推导出整个下载已经完整落盘。

### 状态与执行过程

| 状态层级 | 状态 | 含义 |
| --- | --- | --- |
| 整个队列 | `paused`、`running` | 是否允许当前执行器继续取任务 |
| 未完成任务 | `queued`、`running`、`paused`、`failed` | 等待、执行、已暂停或保留失败信息 |
| 管理条目 | 上述状态，以及 `downloaded` | 综合已保存内容与未完成任务的显示投影 |

`DownloadQueueExecutor` 顺序处理队列项；小说和漫画每项内部的图片传输默认最多并发 3 个。公共处理器重新取得源页面和目标 URL，检查已经存在的离线图片，仅传输缺失部分，并在保存前后校验任务仍存在与取消状态。图片完成记录通过 `work_id` 和当前目标位置写入，迟到回调不能重新创建已删除或替换的任务。

三个业务的提交点不同：

- 漫画在目标图片可用后保存章节源页面及图片引用，完整条目使对应任务退出队列。
- 小说先保存源页面及正文文档，再补齐选定的正文图片；没有目标图片时，正文提交即可结束任务。图片失败时，正文可能已经能够离线阅读，但任务仍未完成。
- 附件先确认响应确实是文件，再发布文件及条目并删除任务。登录页、确认页和普通 HTML 响应不能当成成功附件。

完成后的任务会从未完成队列删除，已下载内容通过独立管理投影展示，不能把“队列中没有这项”单独当作“下载成功”。

### 暂停、取消、重试与身份变化

- **暂停** 取消并等待当前 worker，持久化队列暂停状态，保留任务及已完成文件。继续时重新核对本地图片，而不是相信旧的完成计数。
- **取消任务** 先停止并等待 worker，再删除所选任务和不再被引用的图片；如果原队列在运行，剩余任务继续同一逻辑轮次。取消未完成任务与删除已下载条目是不同操作。
- **下载失败** 保存该项错误并暂停队列，不无限自动重试；用户继续队列时将失败项恢复为待执行，重新获取所需内容。
- **重启恢复** 仅在首次恢复成功后记录完成。上次为运行中的队列变为暂停，等待用户继续；失败的恢复必须传播或允许后续重试，不能冒充空队列。
- **账号变化** 使旧 executor 失效，等待已获准的命令和 worker 收尾后最终暂停。旧 UI 命令不能借用新账号凭据继续修改队列。
- **漫画身份合并** 在移动引用前停止并等待 worker；合并提交后再恢复原队列意图。更换 worker 代次不等于创建一个新的用户后台申请。

队列使用设备共享存储；切换账号后的继续操作使用新会话重新请求缺失内容，不能据此承诺跨账号的论坛访问权限不变。

## 4. 完整性、观察和空间统计

漫画的章节下载状态同时要求有效的源页面、非空图片引用、每张图片的资产记录及文件存在。源页面存储记录 schema、指纹和字节数，用于验证与解码。图片存在性检查不读取所有图片字节；真正加载时若文件缺失或为空，会移除失效资产记录并返回未命中。

小说可以先保存正文、后补图片，下载面板也区分已保存页与仍在队列中的页。管理快照是条目和任务的联合投影，**不是对全部文件逐个解码的完整性扫描**；不能用它证明所有漫画图片均能解码、所有附件尚在磁盘，或没有未登记文件。

`downloadUpdates()` 是有界多播的失效通知，元素不是增量记录。消费方订阅后重读所需快照，并检查视图或账号代次。队列列表、运行状态与管理快照通过抛错区分“读取失败”和“确实为空”；UI 保留既有数据、显示错误，不把失败计为零或自动触发新的继续操作。跨业务身份事务只在提交后发送失效通知，存储包装器也必须转发。

空间统计有明确口径：

- 下载总量按数据库登记的图片资产、小说条目、漫画源页面和附件字节数汇总。同 URL 的共享图片资产全局只登记一次。
- 分组或条目的统计包含该组引用的共享图片；同一图片被多个组引用时，分组数字相加可能大于全局资产量，也不代表删除某组必然释放同样大小。
- 封面量包含索引估算及封面文件占用；普通图片缓存先刷新暂存写入与删除，再读取文件分配空间。
- 设置页展示的是这些分类的统计或估算，不是整个 App 沙箱、SQLite WAL、所有系统缓存及文件系统开销的精确扫描。有不可用分类时，总量不能展示成已知分类的伪完整总和。

## 5. 图片管线与授权上下文

调用方传入 `YamiboImageSource`，描述 URL、Referer、离线范围和 `.content` / `.cover` 用途。Core 的 `YamiboImagePipeline` 负责字节；UI 的 `YamiboUIImagePipeline` 负责解码、显示尺寸变体和内存缓存，不重复实现 Cookie、下载查找或磁盘缓存。

封面请求优先查持久化图片，然后按来源查离线下载、普通图片缓存，必要时发网络请求。正文可以复用同 URL 的持久化封面字节，但封面的存活不再依赖普通缓存。离线范围限定源作品：带 `ownerName` 的范围查漫画章节成员关系；只有 `tid` 时查小说线程的图片引用。不能仅凭磁盘存在一个同 URL 文件，就宣称任意作品已经下载。

网络单次共享请求的身份包含 URL、Referer、实际请求 Cookie、User-Agent 和加载代次；不同请求上下文不能只按 URL 合并。会话变化和清理会使旧请求失效，返回数据和 UI 解码结果发布前仍需校验上下文。普通磁盘原始字节的缓存键仍是 URL；这与“网络请求按认证上下文隔离”是两种边界，不应混称为所有本地图片均按账号隔离。

封面 Referer 会清除用户信息、片段和非页面定位参数；外部图片不发送论坛导航来源。论坛封面缺少历史来源时回退到已知帖子或站点 Referer，不捏造漫画章节。认证头、重定向和错误映射由统一网络策略处理，UI 不手工拼装凭据。

### 普通图片缓存的维护

普通图片原始字节使用 Nuke DataCache，默认上限为 512 MiB，不再使用另一份 URLCache 磁盘空间保存图片。缓存初始化失败只禁用磁盘缓存，不阻止 App 启动。UI 解码结果仅驻留内存，不能计入持久化封面或下载空间。

缓存维护在后台队列合并执行，默认延后约 30 秒；超过上限时按访问时间淘汰到上限的 70%。维护期间新增写入只追加必要的一轮，不建立空闲重复定时器；枚举失败不使用不完整统计强行删除。这个上限不是瞬时硬配额，写入和维护之间可能暂时超过限制。

清理普通图片缓存会使在途瞬态加载失效、清除普通字节和解码缓存，但不删持久化封面、不修改下载，也不重置封面授权失败的冷却策略。

## 6. 磁盘目录与清理责任

以下是 App 默认路径；装配根可以注入独立数据库和缓存根目录。不要将模拟器容器 UUID 或机器绝对路径写入业务代码。

| 默认位置 | 内容 | 责任 |
| --- | --- | --- |
| `Library/Application Support/YamiboX/yamibox.sqlite` | 业务数据、下载记录、封面索引、技术缓存索引 | 各 schema 与存储按业务删除，数据库基础设施统一开库与迁移 |
| `Library/Application Support/YamiboX/downloads/` | `images/`、`manga-source-pages/`、`novel-source-pages/`、`attachments/` | 下载存储维护引用和文件；目录排除系统备份，不参与普通缓存淘汰 |
| `Library/Application Support/YamiboX/content-covers/` | URL 摘要命名的封面原图及迁移标记 | 封面存储清理，不交给普通缓存维护器 |
| `Library/Caches/YamiboX/yamibox-cache/<namespace>/` | 论坛页面与阅读器投影 JSON | `DiskCacheStore` 及业务门面；系统可清除，内容可重建 |
| `Library/Caches` 下的 Nuke DataCache | 普通图片原始字节 | 普通图片缓存的容量维护与清理 |
| `Library/Caches/YamiboX/image-load-policy/` | `cover-load-failures-v1.json` | 封面失败冷却状态，不是账号凭据或图片存储 |

下载目录被整体清理后，任何重建路径都要重新设置排除备份属性。已完成下载和封面原图不通过 WebDAV 搬运；[WebDAV 同步](webdav-sync.md)只处理注册的数据集，其中封面同步的是索引、来源与显示偏好。

设置页的清理按数据所有者分流：

- **网页与阅读缓存** 同时清理小说投影、漫画投影和论坛页面缓存，不删除下载、封面、目录和进度。
- **图片缓存** 仅清理普通图片缓存，不将可重建内容提升为封面持久化数据。
- **其他缓存** 清理 HTTP 缓存、签到日期和收藏更新跟踪状态，不是任意扫除整个 Caches 目录。
- **下载管理** 按条目或作品组删除源页面、附件和对应任务；图片只有在漫画、小说和未完成任务都不再引用时才可回收。
- **封面清理** 删除索引、显示偏好与原始图片，并提交同步删除状态，区别于只清理普通图片缓存。
- **完整重置** 由应用重置工作流先协调停止账号相关活动，再分别清理持久化数据和各文件所有者；不是仅删除缓存或强行覆盖整个数据库。

下载清理的部分文件删除失败会记录日志，不能把数据库已提交当作文件系统绝对不存在残留。诊断时要区分逻辑条目已删除、仍被其他组引用和无引用文件残留，不能随意删除整个共享图片目录。

## 7. 持久化封面的引用、迁移与失败恢复

自动 URL 和手动 URL 都构成图片文件引用。强制文字封面、动态开关及当前未显示的备选 URL 不会使已保存图片自动失去引用。换图、同步合并和身份合并后，只有不再被任何索引引用的图片才可回收；临时详情页候选尚无所有者时可以显示，但不留下孤儿封面文件。

封面原图按 URL 的 SHA-256 摘要去重，保存前验证可解码并保留原始字节。已保存文件损坏时移除坏副本，后续允许重新获取，不让无效响应长期遮盖正确图片。手动设置会保存索引并请求保留图片；自动封面可以按需保存已有下载或缓存字节，也可以请求新图片。

清理先提交索引删除与同步删除标记，再清除文件；清理代次及图片加载版本阻止旧请求或旧内存结果重新写回。逐文件删除失败会传播，已完成部分无需回滚，可再次执行清理。不要将失败简单处理为“没有封面”。

旧普通缓存中的封面分离仅在启动迁移时执行：只迁移当前索引引用的 URL，保存成功后才移除旧副本；缺失字节等待按需获取。无效缓存响应被丢弃，但索引保留。全部处理后写入 `.ordinary-image-migration-v1` 标记，封面清理保留这个标记，防止之后正文产生的同 URL 缓存被再次当成历史封面迁入。

封面网络失败策略只对 HTTP 403 建立持久化冷却，按认证身份、URL 和 Referer 区分，连续失败的等待为 30 分钟、2 小时和 6 小时。取消、离线或一般错误不是这一冷却策略。文件中只保存摘要和计数，不保存原始 Cookie。成功解码才解除失败状态，单纯 HTTP 200 不足以证明图片可用；同 URL 的阅读器成功解码也能唤醒封面。更改封面或显式账号转换会使相关失败与在途加载失效；普通缓存清理不绕过冷却，冷启动也不自动消除有效冷却。

## 8. 下载命名升级的兼容边界

当前用户主动保存能力使用 `Download` 命名；技术缓存仍保持 Cache 命名、命名空间和键格式。共享 `ReaderCacheKeyCodec`、`NovelReaderCacheIdentity` 及历史 payload 文件名不因用户术语变化而重命名。

`downloads.v1.naming` 在冻结的漫画身份迁移之后执行：

1. 将数据库同级的 `offline-cache/` 迁到 `downloads/`，保留文件名与内容引用。
2. 保持外键检查开启，将下载专用 `offline_cache_*` 表与索引改为 `download_*`，确保外键引用随表名更新。
3. 保留已完成文件与未完成队列记录，将队列设为暂停，把原运行中的任务改为暂停并清零瞬时速度。

通常同级目录直接原子移动，不复制整套离线文件。新旧目录并存时先检查冲突，再复制核验，全部一致后才移除旧目录；同名异内容、符号链接或不可读目录必须报错，不覆盖目的文件。普通迁移失败交由启动错误处理与重试，不能当作没有旧数据而创建空库。

历史迁移的旧 SQL、旧目录及 schema-1 解码规则保持冻结；只在升级适配中识别旧命名，不全局替换历史记录。设置兼容读旧 `novelOfflineCache`，完整成功解码后才写回 `novelDownload`，不拿默认设置覆盖坏 payload。

旧 `.offlineCache.` 系统下载会话只重连以取消和收尾，新任务使用 `.download.` 标识。升级可复用已经完成的文件，但不保留单个未完成文件的传输字节进度，也不自动恢复上次运行。

## 9. 平台后台任务与验证限制

Core 通过 `DownloadQueueRunObserving` 上报 `DownloadRunID`、进度、终态及绑定原 executor 的暂停闭包。App 启动层创建同一个 `DownloadContinuedProcessingCoordinator`，在 UI 平台层注册系统任务并注入 Core；业务队列不直接导入 UIKit 或 BackgroundTasks。

iOS 26 起，前台用户开始或继续下载时可申请 `BGContinuedProcessingTask`。请求使用 `.queue`，注册、等待或提交失败不会阻塞普通队列执行；系统提供进度活动，不是自定义 ActivityKit Widget。旧系统继续使用既有下载传输能力，不将较新的持续处理接口当作所有系统的保证。

系统回调只能附着到仍有效的逻辑轮次，不能用回调重新启动队列。暂停、失败和完成会取消待调度请求；系统到期或取消回调只暂停原 executor 的原轮次，不查询当前账号再暂停另一个队列。启动时取消旧进程留下的持续处理申请，避免没有存活 executor 的请求恢复旧队列。

整个队列对应一个系统活动，按下载项等权汇总；项内准备、传输、保存按 5%、90%、5% 计入，成功保存后才增加完成数。运行中追加会更新分母，取消项不制造完成数。图片与附件实际接收字节经有界流汇总；未知长度显示接收量，不猜测百分比。普通系统更新最多每秒一次，阶段变化和终态立即更新。

后台运行受系统调度与资源限制，**不能承诺切到后台、系统到期或用户强制结束进程后一直继续**。重启后的队列恢复为暂停。Local App 可以申请前台开始的持续处理任务，但它不支持没有论坛地址参数的后台冷启动；这与前台申请是否可用是不同条件。

验证仅使用签名的 `YamiboX-Local` 和本地论坛，启动参数以[测试 App 启动参数](../tests/launch-arguments.md)为准。需要核对的场景是：重复入队、暂停继续、失败重试、取消正在传输的项、删除组时保留共享图片、缺失文件后的状态修正、账号转换期间迟到回调、普通缓存与封面的独立清理，以及有旧数据的命名升级。

模拟器可以验证前台队列、持久化状态和主要交互，但不能据此证明真机后台活动、锁屏调度或长时间资源限额。截图只能展示实际可得到的状态，不伪造后台成功画面；迁移和文件完整性结论需要真实数据与文件核查，不能只凭页面成功提示。
