# 收藏更新以共享运行驱动，论坛帖子与漫画目录分开检查

## 运行与取消

[收藏更新引擎](../../Sources/YamiboXCore/Library/Application/FavoriteUpdateCheckEngine.swift)以存储的变更流 ID 共享一次运行，而不是让前台监视器和后台任务各自启动。这个 ID 也适用于通过协议注入的存储，不要求存储是引用类型。首次挂起前就登记准备任务和驱动任务；先持久化运行记录再开始网络检查。UI 镜像按字段赋值同步接收变化，保留原先独立发布的时序。观察者直接从[运行登记表](../../Sources/YamiboXCore/Library/Application/FavoriteUpdateActiveRunRegistry.swift)接收进度，只在运行结束后重读已提交的事件；否则每次进度写入都会让多个观察者重复加载全量事件。普通存储变更仍触发重新读取，挂起期间若有新运行则不让过时快照覆盖其进度。没有活跃驱动却载入运行中记录时，将其恢复为中断。读取失败保留已知状态，不视作空库。

用户可以中断当前共享运行；后台过期回调只能中断自己启动的运行。保留运行回执，以便等待那次运行的准备和最终写入，即使其间另一轮已开始。账号切换先停止接纳新运行，再取消并等待旧驱动退出。中断可以先让界面可见，但收尾仍需要提交已得到的结果并保存终态，因此驱动等待不继承取消状态的有限写入任务；它不再执行网络工作。准备阶段中断也要等第一笔写入结束再尝试保存终态。区分底层存储取消错误和真实 SQL/编码失败，避免把后者误作用户操作；写入失败显式呈现，不冒充完成或覆盖先前中断时间。结果与并发已读/忽略的合并见[收藏更新结果合并](0202-favorite-update-result-merge.md)。

## 检查范围与调度

自动运行只由帖子检查配置触发。前台补查和 iOS 后台刷新共用同一到期间隔，后者只给出最早执行时间；失败或中断也计入节流，以免每次前台恢复都立即重试。漫画间隔只决定位于已开始运行中的目录何时到期；如果把两个间隔改成「任一开启即启动」，默认三天的漫画间隔会让帖子检查仍关闭的用户意外获得后台活动。默认的漫画间隔另受相关版面启用智能漫画、已有可用目录两道条件限制。智能档通过最近七天的事件平滑频率，不随单轮结果切换；目录档位更慢，并仅判断漫画事件，避免用论坛回帖的频率驱动有搜索开销的目录更新。参见[后台调度](../../Sources/YamiboXUI/AppEntry/FavoriteUpdateBackgroundScheduler.swift)与[间隔设置](../../Sources/YamiboXCore/Library/Domain/FavoriteLibrarySettings.swift)。

帖子检查只读取首页和多页帖的倒序最新页，不遍历整帖。小说基线必须只代表作者的活动；作者无法识别时不降级成全帖指纹，旧的未限定指纹在第一次成功取得作者范围后重建且不产生虚假事件。部分字段解析缺失时保留已知值；内容时间来自实际发布或编辑时间，漫画单章取首帖发布时间，不用抓取时间、回帖或目录刷新时间替代。刷新可选筛选项时保留启用选择；未解析版面的帖子不应因为禁用别的版面而失去检查资格；成功检查可以修补未知版面，但不会把已删除的收藏重新创建。帖子检查遇离线应结束本轮且不占用单帖失败额度；针对帖子的连续失败才进入退避。参见[内容更新解析](../../Sources/YamiboXCore/Library/Application/FavoriteContentUpdateResolver.swift)。

[漫画检查](../../Sources/YamiboXCore/Library/Application/FavoriteUpdateCheckEngine+SmartManga.swift)按解析出的稳定目录 ID 聚合同一作品的各收藏章，不按标题或单章逐个刷新；独立保留目录目标和关联分类，避免重建帖子目标时抹掉目录基线。界面筛选使用跟踪目录的分类范围，不能用目录 ID 匹配某一收藏条目。只批量读取现有目录，不在这条路径上发起新目录解析。初次以已知章节建立基线，不请求网络，也不把这些章节报告成更新；后续优先检查基于标签的到期目录，限制可能触发搜索限流的其他目录数量且优先最久未查的目录。后台目前只允许一个非标签目录，前台允许三个。刷新使用新建且按版面限定的工作流获取当前会话，向其提供实际目录章节作为缺失搜索词时的候选，且与阅读器共用搜索冷却状态。搜索冷却或服务端限流不是目录失败，不消耗目标的失败额度或推进基线。

## 事件与通知

同一目标尚未处理时累加有一致类型的新增数量，避免下一次检出掩盖原有计数。系统[本地通知](../../Sources/YamiboXCore/Library/Application/FavoriteUpdateCheckEngine+Notifications.swift)也用目标键替换旧通知，避免堆叠；只有授权后才投递。进行中徽标同时考虑未持久化的新检出和最新已读/忽略状态，不能只依赖其中一方。刷新徽标时按实际未读目标保护较新通知；用户确认旧事件不能顺带删掉同一目标随后产生的提醒。
