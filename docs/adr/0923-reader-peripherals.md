# Route peripheral events by owning scene and persist bindings in their native domains

The [peripheral input manager](../../Sources/YamiboXUI/Features/Reader/Shared/Gamepad/ReaderPeripheralInputManager.swift) translates input into logical reader events and dispatches to the last attached consumer (for example, the comments sheet above the reader). Controller and keyboard sources have independent enable switches; capture can preempt delivery even when its source is disabled so the user can always rebind. Reserved inputs are rejected without leaving capture. Thumbsticks report directional-pad elements, but only the actual direction pad supplies fixed direction events.

Keyboard capture and controller capture share routing, not a persisted type (see [ADR 0712](0712-persist-logical-reader-control-bindings.md)). Unlike separate controllers, the coalesced hardware keyboard has no per-keyboard identity. Scene models use UIKit's window-owned keyboard presses instead of also consuming the global coalesced source, preventing duplicate delivery. The keyboard label resolves through the live button's localized name, a small table keyed by HID usage IDs for common keys, then the settings UI's raw-code fallback. Unknown controller aliases likewise fall back at the rendering boundary. The manager observes its settings store including its own writes; the task holds the store but not the manager so deinitialization can cancel the observer.

Rapid vertical [step events](../../Sources/YamiboXUI/Features/Reader/Shared/Gamepad/ReaderVerticalScrollStep.swift) compound against the previous destination, not the offset the in-flight animation has reached. The [chapter comments scroll view](../../Sources/YamiboXUI/Features/Reader/Shared/Comments/ReaderChapterCommentsViews.swift) uses scroll target layout and an item-ID scroll position instead of a list so repeated controller scrolling stays aligned to rows.

The [reader peripheral settings sheet](../../Sources/YamiboXUI/Features/Reader/Shared/Settings/ReaderPeripheralSettingsSheet.swift) composes its own observable settings model and activity because the settings tab is not mounted there; errors and busy state belong to that sheet. Initialization must remain side-effect-free because SwiftUI retains the first state instance and discards later initializer values. Loading runs from the sheet task.
