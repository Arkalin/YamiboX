# Treat Discuz form pages and action results as distinct responses

Parse the specific Discuz notice container before considering whole-body text: including `body` in a selector list makes the ancestor win in document order. Unwrap Discuz's AJAX CDATA envelope before HTML parsing. Check for authentication first, then specific confirmation markers before generic failure words, since an actual confirmation can mention a prior error. This precedence does not make arbitrary page text authoritative; the blacklist workflow verifies remote membership before reporting completion. Its list parser requires page-specific structure so a login/error page cannot replace the local cache with an empty result. Only the primary profile link supplies a blacklist row name; other links in the row are action labels. Share the account-transition lease for writes, and let the session observer handle logout even while a refresh is in flight. A moving list is an incomplete read if it changes the page count or duplicates a user during traversal.

Native forms preserve browser successful-controls semantics, including replacing an action's query on GET, and keep browser-only helper controls and placeholder categories out of user submissions. Remove upload-dialog chrome as well as its controls, since hidden browser UI is not native content. The desktop header's login helper cannot by itself classify a response as a login page. Some touch editors appear before the usual container; reply subject inputs do not establish first-post validation. Extract known literal flags and editor-tab destinations without evaluating page scripts. Editor source must retain indentation and line breaks, not DOM display-normalized text. For blogs, request the complete form without changing the authenticated User-Agent; the touch form can omit privacy and upload controls. The native blog editor submits HTML even if the touch form requests plain text, and whitespace-only passwords are rejected because Discuz otherwise interprets them as public visibility. A missing optional background catalog does not block editing.

A requested route may return a status message, a form or a different page; classify the actual response. A desktop continuation, blocked redirect or page refresh is not permission to send another request automatically; an explicit link lets the user decide. Preserve the shared operation-confirmation policy between native routing and the browser, since a GET can mutate account state and an unconfirmed GET is not automatically safe to replay. Avoid treating textual upload IDs or JSON as downloaded files, and reset attachment progress on a new transport task rather than adding bytes from a discarded attempt. See [network response and redirect policy](../architecture/networking-and-routing.md#3-url重定向与响应分类) and [editor architecture](../architecture/forum-editor.md).
